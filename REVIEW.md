# Код-ревью проекта локального оркестратора

## Обзор

**recipe_runner.py** — исполнитель YAML-рецептов, автоматизирует действия в браузере через CDP (Playwright). Поддерживает DOM-селекторы и vision-операции через `owl_client`. Управляет профилями Chrome, ведёт логирование и реестр вкладок.

**snap.py** (SnapSage) — модуль компьютерного зрения для оркестратора. Отправляет скриншоты в локальную модель Ollama (UI-TARS-2B) для двух задач: `locate` (поиск элемента по описанию) и `describe` (описание состояния экрана). Возвращает координаты или текстовое описание.

**trace_recorder.py** — запись и воспроизведение траекторий действий пользователя в формате JSONL. Позволяет сохранять «золотые» сценарии с пре-/пост-скриншотами и сетевыми событиями, затем проигрывать их через CDP.

Модули соотносятся так: `recipe_runner` — главный оркестратор, вызывает `snap.py` (через `owl_client`) для vision-задач; `trace_recorder` — вспомогательный инструмент для отладки и создания эталонных траекторий.

## Топ-3 улучшения

### 1. recipe_runner.py: утечка ресурсов Playwright (строки 50–54, функция `_connect`)

**Что сейчас:** Функция `_connect(profile)` запускает `sync_playwright().start()`, но нигде не вызывает `p.stop()` для освобождения ресурсов. В `inventory_profiles` (строки 206–231) есть корректный `finally`-блок с `p.stop()`, однако в `_connect` и других местах (например, `_get_page`, строка 265) браузер подключается без гарантии последующей очистки.

**Что предлагаю:** Обернуть использование Playwright в контекстный менеджер или всегда использовать блок `try/finally` с вызовом `p.stop()` и `browser.close()`. Альтернативно — вынести логику подключения в функцию-генератор с `yield` для гарантии очистки.

**Зачем:** Утечка процессов Chromium и портов приведёт к исчерпанию ресурсов после нескольких запусков рецептов. Исправление требует минимальных изменений (добавить 2–3 строки в каждый вызов), но предотвращает серьёзные проблемы стабильности.

### 2. snap.py: отсутствие обработки ошибок сети и таймаутов (строки 40–55, функция `call_model`)

**Что сейчас:** `call_model` делает синхронный HTTP-вызов к Ollama через `urllib.request.urlopen` с фиксированным таймаутом 120 секунд. При недоступности сервиса, битом JSON или превышении таймаута выбрасывается исключение, которое не обрабатывается ни в `main`, ни в вызывающем коде (`owl_client.locate/describe`).

**Что предлагаю:** Добавить обработку `URLError`, `json.JSONDecodeError` и `TimeoutError` с возвратом структурированной ошибки (например, `{"error": "model_unavailable", "details": ...}`). Реализовать механизм retry (2–3 попытки с экспоненциальной задержкой) для временных сбоев сети.

**Зачем:** Оркестратор падает при любой проблеме с моделью, хотя vision — вспомогательная функция. Обработка ошибок позволит продолжить выполнение рецепта (например, попробовать fallback на DOM-селекторы). Трудозатраты: ~15 строк кода, эффект: отказоустойчивость всей vision-подсистемы.

### 3. trace_recorder.py: хрупкая обработка ошибок при replay (строки 161–191, функция `replay`)

**Что сейчас:** При ошибке выполнения действия (например, `page.click` упал) скрипт ловит исключение, записывает результат с `"ok": False` и продолжает цикл. Однако страница может перейти в невалидное состояние (закрыта, навигация прервана), и следующие действия тоже упадут, но это не будет диагностировано.

**Что предлагаю:** После каждой неудачи проверять `page.is_closed()` и `page.url` (на предмет `about:blank`). Если страница недоступна — прерывать replay с явной ошибкой. Добавить опцию `--stop-on-error` для строгого режима отладки.

**Зачем:** Сейчас пользователь видит длинный список failed-действий, но не понимает корневую причину (страница закрылась на шаге 3, а шаги 4–20 обречены). Ранняя остановка сэкономит время отладки. Изменение локализовано в одном месте, не ломает обратную совместимость.

## Риски

### 1. recipe_runner.py, строка 265 (`_get_page`) — неконтролируемое создание вкладок

Функция `_get_page(browser, prefer_url)` создаёт новую вкладку через `ctx.new_page()`, если не нашла существующую с нужным URL. Нет проверки на максимальное количество вкладок в профиле. При частых запусках рецептов возможно накопление десятков вкладок, что замедлит браузер и вызовет утечку памяти.

### 2. snap.py, строки 58–65 (`parse_locate`) — парсинг координат вне диапазона [0, 1000]

Документация (строки 29–31) утверждает, что модель возвращает координаты, нормализованные до 0–1000. Однако regex `r"click\(\s*(\d{1,4})\s*[,;]\s*(\d{1,4})\s*\)"` допускает числа до 9999. Если модель вернёт координаты в пикселях (например, 1920×1080), клик уйдёт за пределы видимой области. Нет валидации и масштабирования.

### 3. trace_recorder.py, строка 60 (`record`) — предположение о существовании контекста

Код `ctx = browser.contexts[0]` предполагает, что первый контекст уже существует. Если браузер запущен без профиля или контекст пуст, возникнет `IndexError`. Это противоречит логике `ensure_browser` из `recipe_runner.py`, которая создаёт профиль с нуля. Требуется проверка `if not browser.contexts: ctx = browser.new_context()`.
